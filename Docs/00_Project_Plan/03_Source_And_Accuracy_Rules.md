# 03 Source And Accuracy Rules

## الهدف

هذا الملف يحدد قواعد الدقة التي يجب الالتزام بها أثناء كتابة المرجع، حتى لا يتحول المحتوى إلى اجتهادات غير موثقة أو خلط بين مفاهيم Godot.

## القاعدة الأولى: Godot 4.x هو الأساس

يجب أن يكون الشرح مبنيًا على Godot 4.x.

إذا وُجد اختلاف معروف مع Godot 3.x، نذكره فقط كملاحظة، ولا نجعله أساس الشرح.

## القاعدة الثانية: التوثيق الرسمي هو المرجع الأساسي

أي معلومة عن:

- الوراثة.
- وظيفة Node.
- هل Node deprecated.
- هل Node experimental.
- الخصائص الأساسية.
- الاستخدام الرسمي.

يجب التحقق منها من Godot official documentation قبل اعتمادها في الفصل.

## القاعدة الثالثة: لا نخلط بين Node و Resource

أمثلة مهمة:

| العنصر | النوع | الملاحظة |
|---|---|---|
| `CollisionShape2D` | Node | يوضع داخل Scene Tree. |
| `RectangleShape2D` | Resource | يوضع داخل خاصية Shape في `CollisionShape2D`. |
| `CircleShape2D` | Resource | ليس Node مستقلًا داخل الشجرة. |
| `Texture2D` | Resource | يستخدمه `Sprite2D`. |

يجب توضيح هذا الفرق في كل فصل متعلق بالتصادم أو الرسم.

## القاعدة الرابعة: لا نقول إن Node يرث من Node2D إلا بعد التحقق

بعض Nodes تستخدم كثيرًا في 2D لكنها لا ترث من `Node2D`، مثل:

- `Timer`
- `AnimationPlayer`
- `NavigationAgent2D`

يجب تصنيف هذه العناصر كـ “Nodes مساعدة داخل مشاهد 2D”، وليس كـ “Node2D descendants” إذا لم تكن كذلك.

## القاعدة الخامسة: فرّق بين ممكن ومناسب

في Godot، أشياء كثيرة ممكنة تقنيًا لكنها ليست مناسبة عمليًا.

مثال:

- ممكن تحريك `StaticBody2D` بالكود.
- لكنه ليس الخيار المناسب للاعب يتحرك ويقفز.
- الخيار المناسب غالبًا هو `CharacterBody2D`.

لذلك يجب استخدام عبارات واضحة مثل:

| العبارة | المعنى |
|---|---|
| ممكن تقنيًا | يمكن فعله لكنه ليس الأفضل غالبًا. |
| مناسب | استخدام صحيح ومدعوم عمليًا. |
| غير مناسب | قد يعمل بصريًا لكنه يسبب مشاكل تصميم أو فيزياء. |
| خطأ شائع | استخدام يقع فيه المبتدئ ويجب التحذير منه. |

## القاعدة السادسة: توضيح deprecated و experimental

إذا كان Node أو API:

- deprecated
- experimental
- له بديل أحدث

يجب ذكر ذلك بوضوح في قسم الملاحظات.

## القاعدة السابعة: لا نخلط بين الرسم والتصادم

`Sprite2D` يرسم صورة، لكنه لا يصنع تصادمًا وحده.

`CollisionShape2D` يصنع شكل تصادم، لكنه لا يرسم شكلًا بصريًا للعبة.

كثير من أخطاء المبتدئين تأتي من هذا الخلط، لذلك يجب تكرار هذا المبدأ في الفصول المناسبة.

## القاعدة الثامنة: كل مثال يجب أن يكون قابلًا للتطبيق

أي Node Tree نكتبه يجب أن يكون منطقيًا داخل Godot، مثل:

```text
Player (CharacterBody2D)
├── AnimatedSprite2D
├── CollisionShape2D
└── Camera2D
```

ولا نضع Nodes بطريقة مضللة أو غير عملية.

## القاعدة التاسعة: لا نبالغ في التعميم

لا نقول:

- “دائمًا استخدم كذا” إلا إذا كان صحيحًا فعلًا.
- “لا تستخدم كذا أبدًا” إلا إذا كان خطأ فعليًا.

الأفضل استخدام صياغات دقيقة:

- غالبًا.
- في معظم ألعاب platformer.
- في الحالات البسيطة.
- عند الحاجة إلى فيزياء حقيقية.
- عند الحاجة إلى كشف فقط.

## القاعدة العاشرة: مصادر رسمية في نهاية الملفات التعليمية

كل ملف تعليمي عن Node أو مفهوم تقني يجب أن يحتوي قسمًا في النهاية:

```md
## مصادر رسمية
```

وتوضع فيه روابط Godot الرسمية عند كتابة الفصل التفصيلي.
