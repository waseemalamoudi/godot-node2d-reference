# 07 Workflow

## الهدف

هذا الملف يحدد طريقة العمل في المشروع حتى يكون بناء المرجع تدريجيًا ومنظمًا وتحت المراجعة قبل رفع أي فصل تفصيلي.

## سير العمل العام

```text
1. اختيار الفصل.
2. تحديد نطاق الفصل والملفات المطلوبة.
3. البحث في التوثيق الرسمي لـ Godot 4.x.
4. كتابة مسودة عربية منظمة.
5. مناقشة المسودة مع المستخدم.
6. تعديل المسودة حسب الملاحظات.
7. اعتماد الفصل أو الملف.
8. رفع الملفات إلى GitHub.
9. الانتقال للفصل التالي.
```

## قاعدة عدم البدء العشوائي

لا نبدأ بكتابة فصل جديد قبل تحديد:

- هدف الفصل.
- قائمة الملفات داخله.
- قائمة Nodes أو المفاهيم التي سيغطيها.
- طريقة الترتيب.
- نوع الجداول المطلوبة.
- الأمثلة العملية المطلوبة.

## مراحل كل فصل

| المرحلة | الوصف | الناتج |
|---|---|---|
| Planning | تحديد محتوى الفصل قبل الكتابة. | قائمة ملفات وخطة محتوى. |
| Research | التحقق من التوثيق الرسمي والمفاهيم. | ملاحظات بحث موثقة. |
| Drafting | كتابة مسودة بالعربية. | ملف أو ملفات Markdown. |
| Discussion | مناقشة المحتوى مع المستخدم. | ملاحظات وتعديلات. |
| Revision | تحسين المحتوى حسب الملاحظات. | نسخة أفضل من الملفات. |
| Approval | اعتماد المستخدم للمحتوى. | إذن بالرفع. |
| Publishing | رفع الملفات إلى GitHub. | Commit في المستودع. |

## قاعدة الرفع

لا يتم رفع أي فصل تفصيلي إلا بعد موافقة المستخدم.

الاستثناء الوحيد هو ملفات التخطيط الحاكمة التي تم الاتفاق على إنشائها أولًا داخل `00_Project_Plan`.

## طريقة تنظيم الفصول

كل فصل يكون مجلدًا مستقلًا داخل `Docs/`.

مثال:

```text
Docs/
├── 00_Project_Plan/
├── 01_Node_CanvasItem_Node2D_Foundation/
├── 02_Node2D_Derived_Nodes/
├── 03_Physics_Nodes_2D/
└── ...
```

كل فصل يحتوي على:

- `README.md` يشرح هدف الفصل وترتيب القراءة.
- ملفات تفصيلية حسب الموضوع.
- جداول ومقارنات عند الحاجة.
- أمثلة Node Tree.
- أخطاء شائعة.
- مصادر رسمية.

## طريقة مناقشة الملفات

الأفضل أن نناقش الملفات الكبيرة على أجزاء:

```text
1. نناقش عنوان الملف ونطاقه.
2. نناقش الهيكل الداخلي.
3. نكتب المسودة.
4. نراجع المصطلحات والدقة.
5. نضيف الأمثلة والجداول.
6. نعتمد النسخة النهائية.
```

## قاعدة التعديلات

إذا ظهرت معلومة أفضل لاحقًا أو اكتشفنا خطأ:

- نعدل الملف مباشرة.
- نذكر سبب التعديل في رسالة commit.
- لا نترك معلومات غير دقيقة بحجة أنها كتبت سابقًا.

## أسماء commits المقترحة

| نوع العمل | مثال commit message |
|---|---|
| إضافة تخطيط | `docs: add project planning docs` |
| إضافة فصل | `docs: add chapter 01 node foundation` |
| تعديل فصل | `docs: refine physics node comparisons` |
| تصحيح خطأ | `docs: fix node inheritance wording` |

## مبدأ العمل النهائي

المشروع يبنى ببطء لكن بدقة. الهدف ليس كثرة الملفات، بل إنتاج مرجع صحيح ومنظم يمكن الرجوع إليه لاحقًا.
